# PS5 Linux Loader — 13.60 port status

## Goal

Extend ps5-linux-loader toward PS5 firmware 13.60 while preserving the existing 3.00–7.61 Linux boot paths.

## Implemented

- Firmware detection accepts 0x1360 (13.60).
- A dedicated off_1360 firmware profile is registered.
- The verified public kernel profile value VMSPACE_VM_PMAP = 0x2e8 is preserved.
- The loader validates HV/backend capability before Linux image mappings or resume preparation.
- Firmware backends are selected through a common descriptor interface.
- 13.60 has a dedicated backend integration point and a fail-closed implementation.
- Missing 13.60 profile capabilities can be reported independently from the raw offset structure.
- A static regression test verifies the 13.60 profile and backend gate.

## Phase 3 status

The loader-side integration framework for a 13.60 HV implementation is complete.

The backend contract is represented by:

- hv_backend_descriptor
- hv_backend_prepare_fn
- firmware-specific required-profile capability bits
- hv_backend_missing_requirements()
- hv_profile_validate()

This separates:

1. Firmware profile data.
2. Backend capability validation.
3. Firmware-specific HV preparation.

The existing 3.00–7.61 implementations remain unchanged behind the dispatcher.

## Phase 4 — public research status

Public scene documentation now gives us a more concrete description of the 13.60 HV situation:

- The PS5 Developer wiki documents Slopervisor as a PS5 Hypervisor vulnerability working on 13.60.
- The same documentation attributes the discovery to TheFloW and an independent discovery by Jordy.
- The public description associates the vulnerability with Nested Page Tables / SLAT and notes that the relevant mapping behavior changed in 14.00 or 14.10.
- The wiki currently has an empty Implementation section for Slopervisor.
- Searches of public GitHub repositories and code did not reveal a source-available Slopervisor implementation that can be integrated into this loader.
- The public Relapse chain does provide a 13.60 kernel read/write path, but it does not provide the missing Linux-specific Hypervisor backend.

### Architectural consequence

The existing 6.50–7.61 hv_defeat_0607 path should not be copied and retargeted with guessed 13.60 offsets.

The 13.60 backend needs a separately verified implementation whose interface can provide the primitives required by the existing Linux suspend/resume handoff. In particular, the current profile placeholders for:

- KERNEL_CODE_CAVE
- HV_CODE_CAVE_PA
- HV_HANDLE_VMEXIT_PA

must remain unset until they are supported by an actual verified backend.

No VM-exit payload, Hypervisor write primitive, ROP chain, or firmware-specific addresses are synthesized from inference.

## Executable 13.60 path

The branch now contains a real 13.60 executable diagnostic path. After firmware detection and environment setup, it verifies the known 13.60 kernel profile, kernel process/pmap state, kernel virtual-to-physical translation and a scratch kernel R/W round-trip. It then exits normally without entering rest mode, modifying the Linux resume path or invoking the legacy 7.61 HV implementation.

This makes the branch directly testable on a 13.60 console while keeping the Linux handoff fail-closed.

## Current blocker

The project is therefore blocked on one concrete artifact:

a public, source-available and independently verifiable 13.60 Hypervisor implementation suitable for adaptation to ps5-linux-loader.

The absence of that artifact is now a confirmed repository/research finding rather than an assumption based only on the older 7.61 support limit.

## Validation

Run:

    make test

or directly:

    python3 tests/test_13_60_profile.py

The test is static and does not claim that a 13.60 console can boot Linux.

## Next step

When a public 13.60 HV implementation becomes available:

1. Add its firmware-specific backend source.
2. Map only the fields and primitives it demonstrably uses.
3. Add targeted regression tests for the new backend contract.
4. Enable backend_1360.available only after static validation and real-console testing succeed.
5. Keep the existing Linux loader/resume path unchanged wherever possible.
## Phase 4 — independent verification (2026-10-10)

A second, independent research pass re-confirmed the blocker with concrete,
checkable sources. Summary of what is public as of 2026-10-10:

- Relapse-Exploit (`ntfargo/Relapse-Exploit`, public, 7.00-13.60): a WebKit
  browser stage plus an `aio_multi_wait` use-after-free kernel stage giving
  kernel read/write only. `offsets/13.60.js` exposes kernel/userland offsets
  and the chain ships `payloads/elfldr-ps5-1360.elf`, but it contains no
  hypervisor code (no VM-exit interception, IDT redirect, nested-page-table or
  ROP payload). It corroborates `VMSPACE_VM_PMAP = 0x2e8`.
- slopkit (`jordyidk/slopkit`, public, 9.00-12.00): WebKit entry only; it
  registers no HV component.
- Byepervisor (`PS5Dev/Byepervisor`, 1.xx-2xx) and 5XX-Bypervisor
  (`jordyidk/5XX-Bypervisor`, 5.xx): genuine source-available HV exploits, but
  their firmware-specific technique (QA-flags / jump-table) does not map to the
  13.60 NPT/GMET hypervisor and cannot be retargeted by analogy.
- No public repository, code-index hit, or archived wiki page exists for
  Slopervisor. Public reporting (RetroVault, 2026-09-25) states the Slopervisor
  proof of concept was demonstrated on firmware 10.00 with 13.60 "announced as
  the next target", and explicitly describes it as experimental rather than a
  released, source-available jailbreak component.
- Upstream `ps5-linux/ps5-linux-loader` still targets 3.00-7.61 and contains no
  13.60 hypervisor path.

### Conclusion

A source-available, independently verifiable 13.60 Hypervisor implementation
does not exist in public as of 2026-10-10. The placeholder profile fields
(`KERNEL_CODE_CAVE`, `HV_CODE_CAVE_PA`, `HV_HANDLE_VMEXIT_PA`) therefore remain
unset, and `backend_1360.available` remains `false`.

The only remaining prerequisite is outside this repository: either a public,
auditable 13.60 HV implementation, or a real 13.60 console on which a
separately developed implementation can be validated.
